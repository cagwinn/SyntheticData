## Task 1 — SP3.5a Source-code normalisation in `extract_entity_clusters`

**File:** `crates/datasynth-fingerprint/src/extraction/behavioral_extractor.rs`

The v5.13 bundle's `entity_clusters` carries members like `"0"`, `"14"`, `"2"`, `"3"` (corpus numeric Source codes from some clients). The synthetic generator emits SAP-style codes (`"KR"`, `"RV"`, `"DZ"`, ...). The mismatch makes `motifs.neighbors("KR")` return empty.

### Step 1: Add `normalise_source_code` helper to `behavioral_extractor.rs`

After the existing `MAX_SOURCES_FOR_CLUSTERING` / `JACCARD_THRESHOLD` consts, append:

```rust
/// SP3.5a — Canonical SAP-style Source codes the synthetic generator emits.
/// Used by `normalise_source_code` to map heterogeneous corpus codes to
/// the synthetic vocabulary so the motif sampler can actually fire at lookup.
const CANONICAL_SAP_CODES: &[&str] = &[
    "KR", "RV", "DZ", "WE", "RE", "SA", "IM", "KZ", "AB", "AF",
    "DR", "KK", "K9", "KX", "PK", "RB", "RY", "SL", "ZP",
];

/// Map a corpus Source code to the synthetic generator's SAP vocabulary.
/// Unknown codes return `None` — they're excluded from clustering rather than
/// misclassified.
fn normalise_source_code(raw: &str) -> Option<String> {
    let trimmed = raw.trim();
    if trimmed.is_empty() {
        return None;
    }
    if CANONICAL_SAP_CODES.contains(&trimmed) {
        return Some(trimmed.to_string());
    }
    // Best-effort numeric fallbacks observed in the corpus.
    match trimmed {
        "0" | "00" => Some("SA".to_string()),
        "1" | "01" => Some("RV".to_string()),
        "2" | "02" => Some("KR".to_string()),
        _ => None,
    }
}
```

### Step 2: Apply normalisation in `extract_entity_clusters`

Find the existing `pub fn extract_entity_clusters(records: &[Record]) -> EntityClustersPrior`. After the per-Source `attr_sets` BTreeMap is built (but before the pairwise Jaccard loop), insert:

```rust
    // SP3.5a — Normalise Source codes so the resulting cluster members match
    // the synthetic generator's SAP vocabulary.
    let attr_sets: BTreeMap<String, HashSet<String>> = attr_sets
        .into_iter()
        .filter_map(|(raw, set)| normalise_source_code(&raw).map(|canonical| (canonical, set)))
        .fold(BTreeMap::new(), |mut acc, (canonical, set)| {
            acc.entry(canonical).or_default().extend(set);
            acc
        });
```

(Note: `attr_sets` is the variable holding per-Source attribute sets; if the existing code uses a different name, adapt.)

### Step 3: Add a unit test

```rust

        let base = NaiveDate::from_ymd_opt(2022, 1, 1).unwrap();

        for source in ["0", "0", "KR", "KR"] {

```

## Task 3 — SP3.5c Upstream temporal-sampler variance reduction

**File:** `crates/datasynth-generators/src/je_generator.rs`

The per-Source IET sampler from SP3.1 isn't dominant because the upstream temporal sampler still contributes to posting-time variance. When priors are loaded, reduce the upstream contribution.


### Step 2: Inspect the existing sampler API

Likely a method like `temporal_sampler.sample(...) -> NaiveDateTime` or similar. The fix has two viable shapes depending on what's available:

- **Shape A**: the sampler exposes a variance-scale knob (or width parameter) → gate it on `priors.is_some()` and scale by 0.25.
- **Shape B**: no such knob → when `priors.is_some() && iet_sampler.has_source(source_code)`, skip the upstream sampler entirely and use the IET sample as the posting offset.

Implement Shape B (simpler). After the existing temporal-sampler call, conditionally override:

```rust
// Existing call (preserved when priors are None):

// SP3.5c: when priors loaded and IET sampler has per-Source state, prefer
// the IET-driven offset over the upstream temporal sampler's variance.
if let Some(priors) = &self.loaded_priors {
    if priors.iet_sampler.has_source(source_code) {
        // Compute posting_dt from the IET sample instead.
        // (Use the IET accumulator already maintained by SP3.2's je_generator changes.)
        // — Specific replacement depends on the existing IET integration site.
    }
}
```

The exact code depends on how SP3 T11 (IET timing rewire) integrated with the temporal sampler — the IET accumulator may already drive posting_dt; in that case the upstream temporal sampler may already be partially short-circuited, and this task's effect is to reduce any RESIDUAL contribution.

**Pragmatic Step 2 alternative**: if locating the right scope is hard, add a one-line gate:

```rust

// Pass variance_scale through to the temporal sampler if it accepts one;
// else add a `*= variance_scale` to whatever jitter the existing code applies.
```

If even this is intractable, mark T3 DONE_WITH_CONCERNS and proceed to T4. The empirical effect will be measured at the baseline; if P1 Autocorr stays elevated, the issue is somewhere else and we'll learn from the metric.

```rust
pub fn standard_normal_quantile(p: f64) -> f64 {
    use statrs::distribution::{ContinuousCDF, Normal};
    Normal::new(0.0, 1.0)
        .expect("standard normal")
```
