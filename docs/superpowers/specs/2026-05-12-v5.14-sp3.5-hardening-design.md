## 2. Architecture per item

### 2.1 SP3.5a — Source-code normalisation in `extract_entity_clusters`

**File:** `crates/datasynth-fingerprint/src/extraction/behavioral_extractor.rs`

The v5.13 baseline showed that the aggregated `entity_clusters` prior carries 23 clusters but with members like `"0"`, `"14"`, `"2"`, `"3"` — numeric Source codes that some clients in the corpus use. The synthetic generator emits SAP-style codes (`"KR"`, `"RV"`, `"DZ"`, `"WE"`, `"IM"`, ...). When `motifs.neighbors("KR")` is called, the lookup misses because no cluster contains `"KR"` — only the numeric codes.

The fix: **normalise Source codes to the canonical SAP set at the start of `extract_entity_clusters`**, using a small lookup table covering the SAP transaction codes the synthetic generator emits. Unknown codes (true non-SAP IDs) are mapped to a sentinel that effectively excludes them from clustering.

```rust
/// Maps observed corpus Source codes to the canonical SAP-style set
/// the synthetic generator emits. Unknown codes return `None` — excluded from
/// clustering (their attribute sets don't compose with our SAP-coded sources).
fn normalise_source_code(raw: &str) -> Option<String> {
    // Direct SAP-style codes pass through.
    const SAP_CODES: &[&str] = &[
        "KR", "RV", "DZ", "WE", "RE", "SA", "IM", "KZ", "AB", "AF",
        "DR", "KK", "K9", "KX", "PK", "RB", "RY", "SL", "ZP",
    ];
    if SAP_CODES.contains(&raw) {
        return Some(raw.to_string());
    }
    // Common numeric / heterogeneous mappings observed in the corpus.
    // These are best-effort; extending this table is cheap.
    match raw {
        "0" | "00" => Some("SA".to_string()),     // generic GL
        "1" | "01" => Some("RV".to_string()),     // sales billing (heuristic)
        "2" | "02" => Some("KR".to_string()),     // vendor invoice
        // Any other unrecognised code → None (excluded).
        _ => None,
    }
}
```

The mapping is intentionally small — we'd rather exclude unmatched codes than misclassify them. Long-term, we could mine a per-client mapping from each client's data and merge into a canonical vocabulary, but for v5.14 the SAP+numeric subset already covers the dominant cases.

In `extract_entity_clusters`, after the per-Source attribute-set construction, transform the keys:

```rust
let attr_sets: BTreeMap<String, HashSet<String>> = attr_sets
    .into_iter()
    .filter_map(|(raw, set)| normalise_source_code(&raw).map(|canonical| (canonical, set)))
    .fold(BTreeMap::new(), |mut acc, (canonical, set)| {
        acc.entry(canonical).or_default().extend(set);
        acc
    });
```

This deduplicates and unifies attribute sets across clients using the same canonical Source code.

**Test:** synthetic dataset with sources `["0", "KR", "RV"]` all sharing GL accounts `[1, 2, 3]` → after normalisation, the cluster contains `["KR", "RV", "SA"]` (where `"SA"` is the normalisation of `"0"`).

### 2.2 SP3.5b — Calibration-step consumption in `JournalEntryGenerator`

**Files:**
- `crates/datasynth-generators/src/je_generator.rs`
- `crates/datasynth-generators/src/velocity_calibrator.rs` (small extension)

The current `JournalEntryGenerator::generate` invokes `velocity_calibrator.observe_line(...)` and discards the returned `CalibrationStep` (per SP3.4's "framework only" disposition). v5.14 hooks the step into the generator's tunable parameters.

The five rules' target parameters per the SP3.4 spec:
- R6 amount-spike → `amount_config.lognormal_sigma` (bounded [1.0, 4.0])
- R7 off-hours → `posting_off_hours_share` (new field, bounded [0.0, 0.5])
- R8 post-close → `period_close_post_close_share` (new field, bounded [0.0, 0.3])
- R9 round-dollar → `amount_config.round_number_probability` (bounded [0.0, 0.5])
- R10 backdating → `posting_backdating_share` (new field, bounded [0.0, 0.3])

For v5.14, hook the two parameters that already exist on the generator: `amount_config.lognormal_sigma` (R6) and `amount_config.round_number_probability` (R9). The other three (R7/R8/R10) would require new generator state fields — defer those to the same patch only if cheap, else SP3.6.

The hook:

```rust
// In je_generator.rs::generate(), where observe_line is called:
if let Some(cal) = self.velocity_calibrator.as_mut() {
    for line in &entry.lines {
        if let Some(step) = cal.observe_line(line) {
            self.apply_calibration_step(&step);
        }
    }
}

// New method on JournalEntryGenerator:
fn apply_calibration_step(&mut self, step: &CalibrationStep) {
    match step.parameter.as_str() {
        "amounts.lognormal_sigma" => {
            self.amount_config.lognormal_sigma = step.new_value;
        }
        "amounts.round_dollar_share" => {
            self.amount_config.round_number_probability = step.new_value;
        }
        // Other parameters: deferred (would require new field plumbing).
        _ => {}
    }
}
```

`apply_calibration_step` reads `step.new_value` directly because the calibrator already enforces bounds. Adapt `CalibrationStep.parameter` strings to the actual fields the calibrator emits (the SP3.4 implementation used `"amounts.lognormal_sigma"` and `"amounts.round_dollar_share"`).

### 2.3 SP3.5c — `ConditionalIETSampler` × upstream temporal sampler

**File:** `crates/datasynth-core/src/distributions/conditional_iet.rs`

The SP3.1 copula coupling math is correct in isolation (the unit test confirmed empirical ρ ≈ target ρ within tolerance). The JE_3 comparison didn't shift because the synthetic generator's *upstream* temporal sampler also contributes to the per-Source IET — the copula's coupling only modulates one of two variance sources.

Two viable fixes:
1. **Disable upstream temporal sampling when priors are loaded** — let the IET sampler be the sole driver. Cleanest but riskier (the upstream sampler also drives intra-day distribution which we don't want to lose).
2. **Reduce the upstream contribution** — when priors are loaded, scale the upstream variance down to a small fraction. Preserves intra-day pattern but lets the IET sampler dominate the day-to-day cadence.

v5.14 takes option (2): when `loaded_priors.is_some()`, scale the existing per-day timing variance down by a factor (e.g., 0.25) so the IET sampler dominates. Located in the je_generator's day-loop where the existing sampler is invoked — guarded by `if let Some(_priors) = ...`.

Concretely, in je_generator's `generate_for_day` (or equivalent), find where the existing temporal sampler produces a posting datetime and adjust:

```rust
// Existing:
let posting_dt = self.temporal_sampler.sample(...);
// New (gated):
let posting_dt = if self.loaded_priors.is_some() {
    self.temporal_sampler.sample_with_variance_scale(0.25, ...)
} else {
    self.temporal_sampler.sample(...)
};
```

The exact mechanism depends on the existing temporal sampler's API — find via grep, adapt accordingly.

If the temporal sampler doesn't expose a variance-scale knob, alternative: skip the upstream sampler entirely when priors are loaded AND the IET sampler has a per-Source state (i.e., `iet_sampler.has_source(source_code)` is true). Use the IET sample directly as the posting offset.

### 2.4 BUG1 — `copula.rs::standard_normal_quantile` sign-inverted tails

**File:** `crates/datasynth-core/src/distributions/copula.rs`

The SP3.1 implementing subagent flagged a pre-existing bug in the tail branches of `standard_normal_quantile`: for |z| > ~2.05, the function returns the wrong sign. The SP3.1 work avoided this by implementing its own `inverse_standard_normal` via `statrs`. v5.14 fixes the original to match.

**Steps:**
1. Find the function in `copula.rs`.
2. Identify the sign error in the lower-tail and upper-tail branches.
3. Replace with a `statrs::distribution::Normal::inverse_cdf(p.clamp(1e-12, 1.0 - 1e-12))` call (matches what SP3.1 did inline).
4. Add a regression test: assert `standard_normal_quantile(0.025) ≈ -1.96` and `standard_normal_quantile(0.975) ≈ +1.96`.
5. Verify the existing copula tests still pass (they should — they only tested |z| < 2 where the bug was masked).

### 2.5 LOOSE1 — Document bundles as behavioral-only

**Files:**
- `docs/real-world-priors.md`
- `CLAUDE.md`

Add an explicit paragraph (under "What each prior captures") that the committed `industry_priors_*.dsf` bundles contain ONLY the `behavioral.yaml` section (plus minimal manifest/schema/statistics/privacy_audit shells). They are not full fingerprints — the statistical/correlation/integrity/rules/anomaly sections are intentionally empty because the parquet input path bypasses the legacy CSV-based extractor.

If a downstream consumer needs full statistical fingerprints from parquet input, the path forward is either (a) convert parquet to CSV first and re-run `fingerprint extract` without `--behavioral`, or (b) wait for a future "parquet-native fingerprint" sub-project (v5.15+ if anyone requests it).

### 2.6 LOOSE2 — Don't emit empty mandatory YAML sections

**File:** `crates/datasynth-fingerprint/src/io/writer.rs`

When `SchemaFingerprint::tables.is_empty()` and `StatisticsFingerprint::per_column.is_empty()`, the `.dsf` ZIP shouldn't carry these YAML files at all — they currently get written even though they're empty defaults, adding noise to the bundle.

Change the writer to skip empty schema/statistics sections (analogous to the existing `if let Some(...)` gating for the optional sections). The reader must already handle missing schema.yaml / statistics.yaml gracefully (the manifest's `checksums` map drives reads) — verify this path works.

If the reader can't handle missing schema/statistics (because they're "required" in its data model), this loose end becomes more invasive — in that case, defer to a separate "bundle-format-cleanup" patch.

## 3. Testing strategy

- **SP3.5a**: synthetic corpus with mixed Source codes (`["0", "1", "KR", "RV"]`) — assert that after `extract_entity_clusters` runs, the resulting cluster members are all SAP-style canonical codes.
- **SP3.5b**: hand-built `VelocityCalibrator` with a known `CalibrationStep` pending; invoke `apply_calibration_step` on a `JournalEntryGenerator`; assert that `amount_config.round_number_probability` (or `lognormal_sigma`) updates to `step.new_value`.
- **SP3.5c**: integration smoke — when priors are loaded, the upstream temporal-sampler-derived variance contribution is observably smaller in the IET distribution.
