## 1. Overview

The Sajja (2026) paper introduces *behavioral fidelity* as a third evaluation dimension for synthetic tabular data — alongside statistical fidelity (column marginals, pairwise correlations) and downstream utility (TSTR AUROC). The four behavioral patterns it formalises (P1 inter-event timing + autocorrelation, P2 burst structure + active lifetime, P3 shared-infrastructure graph motifs, P4 velocity-rule trigger rates) describe how *real entities* behave over time — exactly the signals fraud detection systems and audit-analytics tools actually use.

DataSynth today emits statistical-fidelity scores (Benford, copulas, distribution fits) and ML-readiness scores (TSTR via `datasynth-eval/ml/`), but has **no composite behavioral-fidelity score** and no within-entity IET autocorrelation, no bipartite fan-out evaluation, no degradation-ratio noise-floor anchoring, and no canonical GL velocity-rule set. SP1 closes that gap: a new `crates/datasynth-eval/src/behavioral_fidelity/` submodule that takes a corpus GL parquet and a synthetic-output directory and produces a degradation-ratio-anchored P1–P4 report.

SP1 is shippable on its own. Its outputs feed SP2 (prior extraction), SP3 (entity-aware generation), and SP4 (showcase release), but none of those depend on SP1 being merged before they can be designed.

### 1.1 Primary use case

Run the new CLI subcommand against a recent DataSynth run plus a real GL parquet from the corpus (45 clients, 7 industries, 2-year window) and obtain:

- A JSON + Markdown report containing P1–P4 sub-metrics + composite BF score.
- Per-entity-profile scoring (primary: `Source`; secondary: `TradingPartner`) with disaggregated DRs per metric.
- Noise-floor baseline values from a deterministic 50/50 split of the corpus.
- Synthetic-only intraday structural metrics (P1/P2 at second resolution) reported informationally.
- CI gate exit code (0 = pass, 2 = at-least-one-DR > configured threshold).

### 1.2 Goals

- Implement Sajja's P1–P4 metrics at GL semantics (`Source` as primary entity, `TradingPartner` as secondary, `EntryDate` as day-resolution timestamp).
- Anchor every metric to a noise-floor baseline via the degradation-ratio normalizer.
- Provide an auxiliary structural P2 variant (JE-line-burst length) for the GL-specific multi-line-JE burst phenomenon.
- Compute synthetic-only intraday metrics (P1/P2 at second resolution, off-hours rate) to preserve the richer signal in our synthetic timestamps.
- Define a canonical GL velocity rule set (R1–R10) suitable for both this corpus and future GL data.
- Produce three output formats from one run: JSON (machine), Markdown (human), CSV (downstream plotting / SP4 ingestion).
- Ship a CLI subcommand `datasynth-data behavioral score` with PR-merge-gate semantics.
- Ship golden-fixture integration tests + unit tests with no corpus data committed to the repo.
- Zero changes to existing eval surfaces (`statistical/`, `coherence/`, `ml/`, gates, scenario diff).

### 1.3 Non-goals

- **Generation-time corrections** — fixing the metrics is SP3, not SP1. SP1 only *measures*.
- **Prior extraction** — mining the corpus for distributions/source-mix/etc. is SP2.
- **HF dataset / Gradio Space / paper writeup** — SP4.
- **Generic framework across non-GL domains** — explicitly scoped to GL/JE semantics. Banking/OCEL/payroll behavioral fidelity can be added later by mirroring the module pattern; we do not pay design tax for it now.
- **Head-to-head against CTGAN/TVAE/GaussianCopula/TabularARGN** — would require Python SDV harness; explicitly deferred to SP4. SP1's `BehavioralFidelityReport` MUST be structurally extensible to accept external generator baselines (i.e., a `generator_id` field and the report can be diffed across runs) so SP4 can drop those in without changing SP1.
- **Corpus data in the repo** — the 45-client corpus stays outside the workspace (referenced via `REAL_CORPUS_DIR`). Tests use a synthetic fixture generated by DataSynth itself; the corpus is referenced only via CLI flags in dev/CI.
- **Privacy-preserving variants** — the existing `datasynth-fingerprint` privacy machinery is not invoked here. SP1 reads parquet rows directly.

## 2. Architecture

### 2.1 Crate placement

SP1 lives entirely inside the existing `datasynth-eval` crate as a new submodule. No new workspace members.

```
datasynth-eval
└── src/
    └── behavioral_fidelity/       [new]
        ├── mod.rs                 public API + re-exports
        ├── config.rs              BehavioralFidelityConfig, EntityProfile, RuleSet
        ├── loader.rs              parquet/csv loader + column normalisation
        ├── entity_profile.rs      EntityProfile::gl_source_tp() and presets
        ├── ietd.rs                P1: IETD W1 + within-entity autocorrelation
        ├── burst.rs               P2: active lifetime + burst length + JE-line-burst
        ├── fanout.rs              P3: fan-out W1 + clustering + triangle log-ratio
        ├── velocity_rules.rs      P4: canonical R1..R10 (GL set) + trigger gap
        ├── degradation.rs         50/50 split noise floor + DR(G, m) normaliser
        ├── intraday.rs            synth-only intraday metrics (info)
        ├── report.rs              BehavioralFidelityReport + JSON/MD/CSV writers
        └── (tests live in `tests/behavioral_*.rs` per crate convention)
```

The submodule **does not modify** any existing eval submodule. It reuses primitives from `statistical/temporal.rs` (autocorrelation), `statistical/anderson_darling.rs` (W1 distance helpers — extract if missing, see §5.1), and the `report::Severity` type from existing eval reports for gate decisions.

## 3. Component design

### 3.1 `config.rs`

```rust
pub struct BehavioralFidelityConfig {
```

YAML-loadable; default profile registered as `gl-source-tp`.

### 3.2 `loader.rs`

Loads a parquet or CSV file (or directory containing one) into a `polars::DataFrame`, normalising column names to a canonical set:

| Canonical name      | corpus source        | Synthetic source              |
| ------------------- | ------------------------- | ----------------------------- |
| `Source`            | `Source`                  | `source_module`               |
| `GLAccount`         | `GL Account Number`       | `account_id`                  |
| `CostCenter`        | `Cost Center`             | `cost_center` (may be null)   |
| `ProfitCenter`      | `Profit Center`           | `profit_center` (may be null) |
| `TradingPartner`    | `Tarding Partner` (sic)   | `trading_partner` (may be null) |
| `JENumber`          | `JE Number`               | `je_id`                       |
| `JELineNumber`      | `JE Line Number`          | `line_no`                     |
| `EffectiveDate`     | `Effective Date`          | `posting_date`                |
| `EntryDate`         | `Entry Date`              | `entry_date` (derived from `created_at` date-part) |
| `CreatedAt`         | (absent — date only)      | `created_at` (RFC3339)        |
| `FunctionalAmount`  | `Functional Amount`       | `amount` (`debit_amount - credit_amount`) |

The loader's column-mapping table is exposed in `EntityProfile::column_aliases` so future profiles can override the mapping. Missing optional columns (e.g., `CostCenter` on the synthetic side) are filled with empty strings; metrics that need them gracefully degrade and emit a warning.

### 3.3 `ietd.rs` — P1: inter-event time + autocorrelation

For a given entity column `E`:

1. Group by `E`.
2. Within each entity, sort by `EntryDate` (day resolution).
3. Compute the IET sequence `δ_i = t_{i+1} − t_i` in days (≥ 0).
4. Pool all IETs across entities → empirical CDF `IETD^E(D)`.
5. Compute `B_1,W^E = W₁(IETD^E(D_real), IETD^E(D_syn))` in days.
6. For each entity with `n_u ≥ 3`, compute lag-1 autocorrelation `ρ_u = Corr(δ_i, δ_{i+1})`.
7. Pool: `ρ̄ = mean(ρ_u)` over entities with `n_u ≥ 3`.
8. Compute `B_1,ρ^E = |ρ̄(real) − ρ̄(syn)|`.

Output: two raw metrics per entity profile. The DR normaliser turns them into degradation ratios.

### 3.4 `burst.rs` — P2: active lifetime + burst length + JE-line-burst

**Active lifetime.** For entity `u`, `AL_u = max(EntryDate_u) − min(EntryDate_u)` in days. Set to 0 for singletons. `B_2,AL = W₁({AL_u}_real, {AL_u}_syn)`.

**Burst length.** For gap threshold `δ ∈ {1, 3, 7} days`, a burst `B_u(δ)` is a maximal contiguous subsequence of `u`'s events with consecutive gaps ≤ `δ`. `L(b) = |b|`. `B_2,BL(δ) = W₁({L(b)}_real, {L(b)}_syn)` pooled across all entities. Report each threshold; composite P2 burst = mean across thresholds.

**JE-line-burst (GL-specific structural P2).** Group by `JENumber`, compute lines-per-JE distribution. `B_2,JEL = W₁({lines_per_je}_real, {lines_per_je}_syn)`. This is *not* time-windowed (all lines share a date) but captures the document-internal burst structure unique to GL.

### 3.5 `fanout.rs` — P3: shared-infrastructure graph motifs

For each `(entity, attribute)` pair in `(primary, attributes_for_p3)` and `(secondary, attributes_for_p3)`:

1. Build bipartite graph `G = (E ∪ A, R)` where an edge `(u, a)` exists iff entity `u` posts at least one row with attribute value `a`.
2. **Fan-out** of attribute `a`: `FO(a) = |{u : (u,a) ∈ R}|`. `B_3,FO = W₁({FO(a)}_real, {FO(a)}_syn)`.
3. **Entity projection graph** `G_E`: connect two entities if they share at least one attribute value. Global clustering coefficient `CC(G_E) ∈ [0,1]`. `B_3,CC = |CC_real − CC_syn|`.
4. **Triangle count log-ratio**: `B_3,△ = |log((triangles_real + 1) / (triangles_syn + 1))|`.

Implemented via `petgraph` for the projection graph and an efficient set-intersection for fan-out and clustering. For our scales (≤ ~1000 entities × ~1000 attributes per profile), this is sub-second.

### 3.6 `velocity_rules.rs` — P4: canonical R1..R10 (GL set)

A velocity rule `r = (feature, op, threshold, window)` triggers at row `(u, t)` if `feature(T_u, t, window) op threshold`. Each entity is classified as triggering r at least once = 1, else = 0. `TR_r(D) = (1/|E|) Σ_u 1_r(u)`. `B_4 = (1/|R|) Σ_r |TR_r(real) − TR_r(syn)|`.

The canonical GL rule set:

| ID  | Feature                                              | Op  | Threshold | Window         | Notes |
| --- | ---------------------------------------------------- | --- | --------- | -------------- | --- |
| R1  | JE count per Source per business day                 | >   | 5         | 1 business day | "Burst posting" — analog of card-fraud R1 |
| R2  | Distinct GL accounts touched per Source per day      | >   | 10        | 1 day          | Account spread |
| R3  | Sum \|FunctionalAmount\| per Source per day           | >   | p90       | 1 day          | Threshold = 90th percentile of per-Source-per-day sums on real_A (data-driven) |
| R4  | Dormant-account activity (Source posts to account inactive ≥ N days) | >   | 0         | 180-day inactivity | "Wakening accounts" |
| R5  | Distinct Trading Partners per Source per day         | >   | 3         | 1 day          | Counterparty spread |
| R6  | max(amount) / median(amount) per Source              | >   | 3.0       | 30 days        | Amount spike (analog R6 in paper) |
| R7  | Off-hours posting (Entry weekday ∈ {Sat, Sun})       | >   | 0         | per row        | Off-hours signal |
| R8  | Post-close posting (EntryDate > period_end + 5bd)    | >   | 0         | per row        | Late posting (period close drift) |
| R9  | Round-dollar share (\|amount\| mod 1000 == 0)         | >   | 0.10      | per Source     | Round-number concentration |
| R10 | Backdating (EffectiveDate − EntryDate > 30d)         | >   | 0         | per row        | Backdated posting |

R3's threshold (p90) is **data-driven**: computed on `real_A` of the 50/50 split, applied to all three datasets (real, real_B, syn). This matches Sajja Table 1 R3 which uses an absolute $1000 threshold; we generalise to a percentile because GL amount scales vary by client/industry.

R7-R10 are *flag-rules* (single-row predicate, no aggregation window) — included because they are the natural GL analogues of velocity behaviour. They are GL-domain extensions; their inclusion is a deliberate departure from the paper.

Each rule emits `TR_r ∈ [0, 1]` per dataset. `B_4` is the mean abs gap.

### 3.7 `degradation.rs` — degradation ratio normaliser

For a given metric `m`:

1. Deterministic 50/50 split of `real` via `seed`: every JE Number is assigned to half A or half B by `hash(je_number, seed) mod 2`. Split is by JE Number (not row) so multi-line JEs stay together.
2. `baseline_m = m(real_A, real_B)`.
3. For each `(metric m, synthetic G)`: `DR(G, m) = m(real, syn_G) / baseline_m`.
4. If `baseline_m == 0` (perfect noise-floor — unlikely but possible for autocorr-gap), use `baseline_m = ε = 1e-9` and emit a warning.
5. The composite BF score is the equal-weighted mean of all sub-metric DRs.

### 3.8 `intraday.rs` — synth-only structural metrics

These metrics are computed on `syn` only (and `real_A`/`real_B` for sanity but `real` lacks the required column). They are informational and **not** part of the composite BF score:

- `P1_intra_w1_seconds`: pooled within-entity IETD in seconds.
- `P1_intra_autocorr`: pooled lag-1 autocorr at second resolution.
- `P2_intra_burst_len_5min`: burst length distribution at 5-minute threshold.
- `off_hours_rate`: fraction of synthetic rows where `CreatedAt` weekday ∈ {Sat, Sun} or `CreatedAt` hour ∈ {0..5, 22..23}.

If `CreatedAt` is absent on the synthetic side, this section is omitted with a warning.

### 3.9 `report.rs` — output writers

```rust
pub struct BehavioralFidelityReport {
    pub profile:           String,
    pub generator_id:      String,           // e.g. "datasynth-v5.10.0"
    pub seed:              u64,
    pub real_corpus:       CorpusSummary,
    pub synthetic:         CorpusSummary,
    pub noise_floor:       BaselineValues,
    pub per_entity:        BTreeMap<String, EntityMetrics>,
    pub composite_bf_score: f64,
    pub intraday_structural: Option<IntradayMetrics>,
    pub gates:             GateResult,
    pub generator_version: String,           // self-version for reproducibility
}

pub struct EntityMetrics {
    pub p1_ietd_w1_days:    f64,  pub p1_ietd_dr:  f64,
    pub p1_autocorr_gap:    f64,  pub p1_autocorr_dr: f64,
    pub p2_active_lifetime_days: f64, pub p2_active_lifetime_dr: f64,
    pub p2_burst_len_per_threshold: BTreeMap<i64, (f64, f64)>, // (raw, DR)
    pub p2_je_line_burst:   f64,  pub p2_je_line_burst_dr: f64,
    pub p3_fanout_per_attr: BTreeMap<String, (f64, f64)>,
    pub p3_clustering_gap:  f64,  pub p3_clustering_dr: f64,
    pub p3_triangle_logratio: f64, pub p3_triangle_dr: f64,
    pub p4_rule_results:    Vec<RuleResult>,
    pub p4_mean_gap:        f64,  pub p4_mean_gap_dr: f64,
}
```

Three serializers:

- **JSON** (`report.json`) — exact struct dump via serde, no precision loss; consumed by SP4 Space.
- **Markdown** (`report.md`) — human table with DR cells colour-tagged ≤ 1.5 green, 1.5–3 yellow, > 3 red.
- **CSV** (`metrics.csv`) — flat `(entity, metric, raw, baseline, dr)` rows; suitable for pandas/polars/plotting.

## 4. Data flow + privacy

- The corpus is **outside the repo** (set via `REAL_CORPUS_DIR` or passed as a CLI flag). We never copy it in; the CLI accepts a path.
- Tests do **not** depend on the corpus. The golden integration test uses a synthetic fixture generated by DataSynth itself (we run `cargo run -p datasynth-cli -- generate --demo --output target/test-fixtures/bf` in the test setup and use that output as the "real" side, with a second smaller-seed synth run as the "synthetic" side).
- CI (`gh actions`) does **not** touch the corpus. The integration smoke test is purely DataSynth → DataSynth.
- The corpus comparison is dev-loop / manual / SP4 territory.

## 5. Testing strategy

### 5.1 Pre-flight: ensure W1 + autocorrelation primitives exist

Confirm `crates/datasynth-eval/src/statistical/anderson_darling.rs` (or a sibling) exposes a Wasserstein-1 helper; if not, extract one as the first commit of the implementation phase. Same for `temporal.rs` autocorrelation. These should be `pub(crate)` accessible from `behavioral_fidelity/`.

### 5.2 Unit tests (per metric module)

- `ietd_test.rs`: synthetic minimal arrays — all-same-IET → autocorr ≈ 1; alternating short/long IET → autocorr ≈ −0.5; identical real == syn → W₁ = 0.
- `burst_test.rs`: hand-built entity series — known active-lifetime, known burst lengths at given thresholds.
- `fanout_test.rs`: 3-entity-3-attribute graph where two entities share an attribute → clustering coefficient = known value; triangle count = known.
- `velocity_rules_test.rs`: tiny dataframe with one entity violating R1, none violating R7, etc. → trigger rates check out exactly.
- `degradation_test.rs`: `m(real, real)` over identity split → DR = 1.0 ± 1e-9 (the noise floor is itself).

### 5.3 Golden integration smoke

`tests/behavioral_smoke.rs`:

1. Generate two DataSynth datasets with seeds 42 and 43 (small/demo size).
2. Compute the BF report treating seed-42 as "real" and seed-43 as "synthetic".
3. Assert composite BF score is in a sensible range (the two runs differ by RNG; expect DR ≈ 1.0–3.0 across most metrics — exact bounds finalised after first measurement and committed as snapshot).
4. Snapshot the report JSON (sorted, deterministic — guaranteed by `BTreeMap` field types). Regenerate the snapshot via `cargo test -p datasynth-eval --test behavioral_smoke regenerate_golden -- --ignored`, matching the existing repo convention used by `manifest_golden.rs` and siblings.

### 5.4 Round-trip / noise-floor sanity test

`tests/noise_floor.rs`: run the metric pipeline with real_A as "real" and real_B as "synthetic" — assert all DRs equal 1.0 (definition of noise floor).

### 5.5 CI integration

Add to `.github/workflows/ci.yml`:

- `cargo test -p datasynth-eval --test behavioral_smoke -- --test-threads=4` (per repository concurrency policy).
- `cargo test -p datasynth-eval --test noise_floor -- --test-threads=4`.
- Does **not** add the corpus comparison to CI; that is a dev-loop / SP4 concern.

## 6. Dependencies + risks

### 6.1 Dependencies

| Dep            | Status                  | Used for |
| -------------- | ----------------------- | -------- |
| `polars`       | workspace               | DataFrame + parquet IO |
| `ndarray`      | workspace               | array ops if needed |
| `statrs`       | workspace               | autocorrelation, percentile |
| `petgraph`     | workspace (graph crate) | P3 entity projection graph + triangle count |
| `rayon`        | workspace               | parallel per-entity computation |
| `serde`+`serde_json` | workspace         | JSON report |

No new dependencies. No new heavy compile-time cost.

### 6.2 Risks

- **Performance on large corpus files (400+ MB).** Mitigation: parquet column-pruning at load (only need ~10 of 18 columns); rayon for per-entity loops. Worst case we add a `--max-rows` flag. Smoke benchmark on a smaller corpus file first.
- **Memory pressure when building the entity projection graph for P3.** ~24 Sources × ~1000 attributes is trivial; ~hundreds of Trading Partners × ~1000 attributes is fine; if a future profile needs ~10K entities, sparse representation in `petgraph` handles it.
- **corpus column name typo (`Tarding Partner` sic) bleeds into our schema.** Mitigation: the alias table in `loader.rs` is the single source of truth — `TradingPartner` → real column `Tarding Partner` is one map entry.
- **Day-granularity P1 means our W1 is in days, not seconds — different absolute magnitudes than the paper's IEEE-CIS baselines.** The composite DR score is still comparable because each metric is normalised by its own noise floor. We document this in the report's preamble.
- **JE-line-burst is a GL-specific addition not in the paper.** We label it clearly in the report (`p2_je_line_burst`) so future cross-domain comparisons can omit it. It contributes to the composite BF score with equal weight to the other P2 sub-metrics.
- **The `Source` column in real data has 24 distinct values, but synthetic data may use different module codes.** Mitigation: the metrics compute per-entity *behaviour*, not per-entity *identity*. The set of Source values does not need to match between real and synthetic; only the distribution of behaviours per Source does.

## 7. Acceptance criteria

SP1 is done when:

1. **Builds.** `cargo build --release` succeeds; `cargo clippy --workspace` emits no new warnings.
2. **Tests.** `cargo test -p datasynth-eval --test behavioral_smoke -- --test-threads=4` passes. `cargo test -p datasynth-eval --test noise_floor -- --test-threads=4` passes. Unit tests per metric module pass.
3. **CLI.** `datasynth-data behavioral score --help` works. Running against any DataSynth `generate --demo` output + the same generated output (real == syn smoke case) yields composite DR ≈ 1.0.
4. **Reports.** Three artifacts written per run: `report.json`, `report.md`, `metrics.csv`. JSON validates against the documented schema. Markdown is human-readable. CSV has one row per (entity_profile, entity_column, metric_name, raw_value, baseline_value, dr_value).
5. **corpus dry run.** A `cargo run -p datasynth-cli -- behavioral score --real /path/to/corpus-je.parquet --syn ./output --profile gl-source-tp` invocation against a fresh DataSynth demo run produces a non-empty report with non-NaN scores for every metric. Composite BF score is reported.
6. **Gate semantics.** Adding `--fail-on-dr-above 1.5` to a known-bad pairing yields exit code 2; same flag against the real==syn smoke case yields exit code 0.
7. **Docs.** `docs/behavioral-fidelity.md` (new) explains the framework, metric definitions, GL adaptation, and CLI usage. README mentions the new subcommand. CLAUDE.md gets a brief entry under "Evaluation Module".
8. **No corpus data committed.** Repository is clean of `Client Data` paths beyond the spec/docs reference.

## 8. Implementation phases

The implementation plan (written by `writing-plans` skill) will decompose into roughly:

- **Phase A** (~2 days): Scaffolding + `config.rs` + `loader.rs` + entity profile registration + W1/autocorr primitive availability check.

## 9. Out of scope / explicit deferrals

- **SP2 (Real-World Prior Extraction).** SP1 only reads the corpus; it does not derive distributions from it.
- **SP3 (Entity-Aware Generation).** SP1 only measures; the actual within-entity IET state machine, bipartite fan-out generator, and velocity-rule calibration objective are SP3.
- **SP4 (Showcase Release).** No HF dataset, no Gradio Space, no head-to-head against external generators. SP1's report schema is structured to make these additions in SP4 trivial.
- **Other domains (banking, OCEL, payroll, manufacturing).** GL only. Mirror the pattern when needed.
- **Privacy-preserving evaluation.** The corpus is already obfuscated; we treat it as plaintext input. Differential privacy / k-anonymity scoring is not part of behavioral fidelity per se.
