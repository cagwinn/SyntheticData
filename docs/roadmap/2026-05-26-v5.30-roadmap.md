The eval gaps with the cleanest fixes. Each should ship as one focused PR.

#### A1. **P3 graph motifs wired into Sajja exact eval**
- **Why:** Sajja's framework includes P3 (shared-infrastructure graph motifs).
  Today's run *skipped* P3 because we didn't pass `merchant_col` /
  `device_col`. The paper's row-independent generators are stuck at 81-99×
  on P3 (TabularARGN 17.2× being the best). DataSynth's row-aware joint
  generation should excel here — it's exactly the lever where Proposition 1
  binds the competition.
- **What:** Update the Sajja driver at `~/regen/run_sajja_eval.py` (committed
  to repo) so `merchant_col = 'trading_partner'` and `device_col = 'gl_account'`
  flow through. Re-run on (reference, v5.29 synth).
- **Expected outcome:** P3 DR 5-15× (would be DataSynth's strongest absolute
  number against the paper).
- **Effort:** ~½ day (script tweak + 30-min eval re-run on VM).
- **Task:** TBD.

#### A2. **P4 velocity rules on synth labels (eliminate NaN)**
- **Why:** Today P4 is NaN because the reference shard has no fraud labels
  and we used a top-4 % amount heuristic (which produced zero velocity-rule
  violations on the reference half-split). Use the synth's own `is_fraud`
  column as ground truth on *both* halves of the synth evaluation; reference
  remains unlabelled (acceptable — Sajja's eval supports that path).
- **What:** Adjust the driver to keep label heuristic on reference, use real
  `is_fraud` on synth. Re-run.
- **Expected outcome:** P4 DR populates (typically 5-20× range based on
  Sajja's published bands). Composite drops the NaN; goes from 4 valid
  metrics to 5.
- **Effort:** ~½ day.
- **Task:** TBD.

#### A3. **Reduce SP3 synthetic Z-tail mass (TAIL_MASS 0.30 → 0.15)**
- **Why:** Capstone Stage 2 fingerprint shows synth has 526 distinct sources
  vs ~287 on the reference. Source-cardinality bloat comes from
  `behavioral_priors.rs:338`'s 500-code Z-tail at TAIL_MASS=0.30. Halving
  the mass cuts the tail's representation, compressing per-source IET
  distributions toward reference.
- **What:** Change one constant in `behavioral_priors.rs`. Re-run BF + Sajja
  exact eval.
- **Expected outcome:** vol-corrected composite -10 to -15 % (current 65.8×
  → ~55×). Trades off some IET-variance lift (the SP3 design intent of the
  Z-tail) for tighter source distributions; document the trade-off in
  FINDINGS.
- **Effort:** ~½ day (1-line change + re-eval).
- **Task:** TBD.

### Tier B — medium effort (~1 week each)

Structural fixes that move the underlying generator behavior, not just the
measurement.

#### B1. **Per-source IET sampler refinement (closes P1 autocorr gap)**
- **Why:** P1 autocorr DR is 105.9× — our worst single Sajja sub-metric.
  Root cause: per-source events emitted by independent process generators
  with their own marginal IET distributions, no within-entity temporal
  coupling. The capstone fingerprint independently confirms this (synth
  edge density 91× higher than reference because per-source events spread
  thin across 526 sources).
- **What:** Two viable paths, evaluate both:
  - **Process-family clustering** — group synthetic sources into 5-10
    process families (P2P, O2C, R2R, period-close, manual) and sample IETs
    from a family-shared distribution rather than per-source. *Manufactures*
    positive per-source autocorrelation.
  - **Active-window enforcement** — extend SP3's `MultiSegmentActiveWindow`
    so consecutive events on the same entity are deterministically ordered
    within a session/burst, giving correlated short IETs.
- **Expected outcome:** P1 autocorr DR 106× → 20-40× (the band TVAE achieves
  at 5.9× post-conditional-sampling). Vol-corrected composite -25-30 %.
- **Effort:** 5-7 days incl. tuning + regen.
- **Task:** TBD.

#### B2. **Heavy-tail outlier emission (opt-in anomaly type)**
- **Why:** Capstone shows synth relational_score p99 12.3× vs reference 20.0× —
  we SUPPRESS heavy-tail outliers via `lines_per_je_cap=100` +
  bridge-account-allowlist. Right for ML training, wrong for anomaly-detection
  benchmark realism. The reference shard's heavy tail comes from real
  consolidation entries / period-end accruals / manual reclasses; we don't
  generate those at the same magnitude.
- **What:** New anomaly type `ConsolidationOutlier` that emits multi-100-line
  JEs touching bridge accounts, opt-in via config. Frequency calibrated to
  match reference shard's p99/max relational_score percentiles.
- **Expected outcome:** Synth p99 relational_score 12× → 18-22× (matches
  reference). Net effect on BF composite: ambiguous — the metric tightens
  in some places, loosens in others. The HONEST win is downstream:
  anomaly-detection benchmarks become more credible.
- **Effort:** 5-7 days (anomaly type + calibration + re-eval).
- **Task:** TBD.

#### B3. **Per-process fraud rate distributions (closes GNN headroom)**
- **Why:** GNN AUC 0.919 is consistent across processes (0.914-0.925) but
  *too* flat — real audit data has process-specific fraud signatures.
  `fraud.fraud_rate` is currently global.
- **What:** Implement `fraud.per_process_rates: { R2R: 0.06, P2P: 0.04, ... }`
  in the schema + wire through `je_generator`. Calibrate against per-process
  empirical bands.
- **Expected outcome:** GNN AUC 0.919 → 0.93-0.94, per-process variance
  widening to a more realistic 0.88-0.95 spread.
- **Effort:** 4-5 days.
- **Task:** TBD.

### Tier C — research-scope (~2-4 weeks each)

Paradigm-level fixes. Won't ship in v5.30; queued for v5.31+.

#### C1. **Streaming aggregate (closes group-audit OOM architecturally)**
- **Why:** The #148 patches (row_budget scaling + Custom volume) make
  enterprise_2000 fit, but the aggregate phase still loads all 2000 trial
  balances into memory simultaneously. An entity_count=20000 regen would
  still OOM. The right fix is streaming/incremental aggregation:
  process TB-by-TB, persist running totals between steps.
- **What:** Refactor `datasynth-group/src/aggregate/` to use a
  rolling-accumulator pattern (~500 LOC). Trial-balance accumulator,
  IC-matching index, FX translation buffer — all streamed from disk.
- **Expected outcome:** Group regen scales to 10K+ entities on a 64 GB box.
  Unblocks the multi-shard BF noise floor (D1).
- **Effort:** 2-3 weeks.
- **Task:** TBD (will subsume #148 architectural intent).

#### C2. **Multi-period generation with prior-year carry-forward**
- **Why:** Real audit work depends on prior-year comparatives + cross-period
  accrual reversals + roll-forward schedules. Today's audit datasets emit
  12-month single-year data. `SessionSchemaConfig` exists in the schema
  but is barely wired into the audit path.
- **What:** Fully wire multi-period generation. Prior-year JEs emit with
  matching account + counterparty references; opening balances derived from
  prior-year close; cross-period accrual reversals.
- **Expected outcome:** Audit datasets become production-realistic.
  P2 active lifetime DR (currently 86.8×) compresses substantially as
  cross-period entity activity emerges. Unlocks "DataSynth replaces multi-
  year audit data" use cases.
- **Effort:** 3-4 weeks.
- **Task:** TBD.

#### C3. **Adversarial calibration loop (closes the paper-headline gap)**
- **Why:** Sajja's paper explicitly calls out that none of the tested
  generators "train against velocity-rule preservation as an explicit
  objective". DataSynth's rule-based generator can be calibrated against
  a learned detector's residuals as a closing-the-loop training signal.
- **What:** GNN-in-the-loop: train fraud detector → compute residuals →
  feed top-residual patterns back as anomaly-type targets for the next
  generation iteration → re-train.
- **Expected outcome:** All Sajja sub-metric DRs drop into single digits.
  Paper-headline: "DataSynth achieves <10× DR on every Sajja P1-P4
  sub-metric" — first synthetic generator to do so.
- **Effort:** Months.
- **Task:** TBD (probably becomes its own multi-month track).

## Sequencing for the autonomous loop

Loop picks the next-available task each wake; priority within each tier is by
task ID. Sequence:

1. **A1** → A3 → A2 (Tier A: ship 3 PRs in week 1)
2. **B1** → B3 → B2 (Tier B: 3 PRs over weeks 2-4)
3. Bench checkpoint — re-run all BF + Sajja evals after Tier A+B; commit
   updated dataset cards + capstone fingerprints
4. **C1** → C2 (Tier C: 4-8 weeks)
5. C3 + D1 + D2 in parallel as they unblock
6. Continuous: HF dataset card refresh after each tier completion

## Privacy / legal — autonomous-loop discipline

- All eval/training data scoped to runtime args; no paths in commits
- Aggregate stats only in committed artefacts (per
  `feedback_corpus_vague_reference`)
- HF token never persisted; env-only during pushes
- Engine commits: `cargo test -p <crate> --lib` + `cargo clippy` + `cargo fmt
  --check` BEFORE each push (per CLAUDE.md)
- VM is short-lived compute substrate; corpus shards copied for the session
  and removed at decommission

## Wake cadence

- Hourly (3600s) during active work hours
- Each wake picks next task by tier+ID, ships ONE incremental commit, opens
  next PR or progresses an in-flight one
- After Tier A completion, re-baseline BF + Sajja and update HF cards
- Stop autonomous loop on explicit user instruction OR when all roadmap items
